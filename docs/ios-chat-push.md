# Чаты и push в iOS

## События в реальном времени

Подключите WebSocket `wss://<домен>/apisup/supply/ws` с cookie сессии соответствующего сайта. Сервер определяет пользователя по cookie; необязательный `?user_id=...` должен совпадать с пользователем сессии. Без действительной cookie соединение закрывается с кодом `4001`. Убедитесь, что прокси передаёт заголовки Upgrade/Connection и Cookie.

Сообщение `"ping"` возвращает `"pong"`. Для индикации набора отправляйте JSON:

```json
{"type":"typing","chat_id":123,"is_typing":true}
```

При остановке отправьте `is_typing: false`. Сервер проверяет членство в чате и рассылает другим участникам событие `typing` с `chat_id`, `user_id`, `user_name` и `is_typing`. Клиенту следует обновлять `true` примерно раз в 2–3 секунды и скрывать индикатор через 5 секунд без обновлений: при потере соединения событие остановки может не прийти.

Событие `new_message` содержит `chat_id`, `chat` (тип и идентификаторы связанной сущности) и `message` с `sender`, текстом и вложениями. Оно предназначено для отображения уведомления при открытом приложении. Вложение может появиться после сообщения: тогда придёт `message_updated` с обновлённым списком вложений. При переподключении запросите историю и счётчики заново; WebSocket не гарантирует доставку в отсутствие соединения.

В каждом вложении поле `url` — относительный URL получения файла. Для картинок JPEG/PNG/GIF/WebP ответ имеет тип изображения и отображается inline. Требуется та же cookie сессии, а пользователь должен состоять в чате. В iOS передавайте cookie при загрузке изображения; обычный публичный URL без авторизации не предусмотрен. Префикс URL при необходимости задаётся `CHAT_PUBLIC_API_PREFIX` (по умолчанию `/apisup/supply`).

## Настройка APNs

1. В Apple Developer зарегистрируйте App ID с Bundle ID приложения и включите Push Notifications; в Xcode у цели включите capability Push Notifications и настройте signing с нужной командой. Для обычных уведомлений фоновый режим не обязателен.
2. В Certificates, Identifiers & Profiles → Keys создайте APNs Authentication Key, скачайте `.p8` и сохраните его вне репозитория. Запишите Key ID и Team ID. Не передавайте ключ в чат и не добавляйте в Git.
3. На сервере установите зависимости из `requirements.txt` (включая HTTP/2 для httpx) и укажите в `.env`:

```dotenv
APNS_TEAM_ID=XXXXXXXXXX
APNS_KEY_ID=XXXXXXXXXX
APNS_KEY_PATH=/путь/вне/репозитория/AuthKey_XXXXXXXXXX.p8
APNS_BUNDLE_ID=ru.example.app
```

`APNS_BUNDLE_ID` должен точно совпадать с Bundle Identifier и APNs topic приложения. Перезапустите сервер. `.p8` должен читаться пользователем процесса backend.
4. Приложение запрашивает разрешение через `UNUserNotificationCenter`, вызывает `registerForRemoteNotifications()` на main thread, получает device token из `application(_:didRegisterForRemoteNotificationsWithDeviceToken:)`, переводит его в hex и после авторизации отправляет `PUT /apisup/supply/push/ios/device` с cookie сайта:

```json
{"token":"<hex device token>","environment":"development"}
```

Для сборки с APNs production entitlement передавайте `"production"`. Окружение зависит от entitlement и профиля подписи, а не только от наличия DEBUG. Вызывайте регистрацию при каждом получении токена и после входа в аккаунт. При выходе отправьте `DELETE` на тот же путь с тем же JSON и cookie до удаления сессии. Для другого сайта регистрируйте токен отдельно в сессии этого сайта.
5. В обработчике открытия уведомления используйте поля `type`, `object_type`, `object_id`, `related_user_id` для перехода в чат или задачу. Обрабатывайте foreground-уведомления через `UNUserNotificationCenterDelegate`. При включённом WebSocket клиенту стоит подавлять дублирующий баннер для одного события.

Сервер отправляет push для событий `chat_message` и `task_assigned`; в payload есть `aps.alert`, `aps.sound` и поля маршрутизации. Это отдельная доставка от Web Push. Токены хранятся отдельно в базе каждого сайта; APNs 410 и ошибки недействительного токена деактивируют запись. Проверьте реальную доставку на устройстве с корректным provisioning и настройками уведомлений. Очередь отправки находится в процессе сервера и не переживает его перезапуск; APNs не гарантирует немедленную доставку. Данные уведомления не заменяют загрузку актуального состояния из API.
